# Build roadmap

Phased so each phase is independently demoable. See `docs/architecture.md`
for rationale and `protocol-spec.md` for the wire format each phase builds
against. Status reflects this repository's current state — update it in the
same PR that finishes a phase's work.

## Phase 0 — Validation spikes (de-risk before building the real thing)

These are hardware checks, not code — they can't be verified by an agent
without a physical Windows machine and Android device. **Status: not yet
performed against real hardware in this repository's history** — the code
in this repo is written to the documented APIs but is unverified on-device.
If you have the hardware, please run these and report back (an issue or a
note in a PR is fine).

What *has* been verified without hardware: `windows-app`'s full test suite
(`cargo test`/`clippy`/`fmt`) passes, and on the Android side every
platform-independent module (`AudioPacket`, `ControlMessage`, `Crypto`,
`JitterBuffer`) was compiled and unit-tested with the project's actual
Kotlin/`kotlinx` toolchain versions on a plain JVM — including a
cross-implementation known-answer test where Android's
`Cipher.getInstance("ChaCha20-Poly1305")` decrypts a ciphertext generated by
`windows-app`'s Rust crypto code and recovers the exact same plaintext (see
`android-app/README.md` → Testing). What's *not* verified is anything
touching the Android Gradle Plugin/SDK or actual hardware — WASAPI capture,
`AudioTrack` routing, and mDNS/NSD end-to-end.

- [ ] Confirm WASAPI loopback capture works from a non-admin account on the
      target Windows version; dump captured audio to a `.wav` file and
      listen back.
- [ ] Confirm `AudioTrack` in low-latency mode + `USAGE_MEDIA` actually
      routes to A2DP earbuds (not the phone speaker) by playing a
      locally-generated test tone.
- [ ] Confirm mDNS advertise/browse works over an actual Android hotspot
      (not just a home router) — the topology most likely to have
      surprises.
- [ ] Confirm the Phase 4 network-change path recovers on a real device:
      switch Wi-Fi networks mid-stream, and drop to mobile data and back,
      and check discovery restarts and the session re-establishes. The
      callback wiring is written against the documented
      `ConnectivityManager` behaviour but has never run on hardware.
- [ ] Confirm the Phase 5 drift correction holds over a multi-hour session
      against two real clocks — latency should stay put rather than creeping,
      with no audible artefacts from the frame-level corrections.

## Phase 1 — Minimal end-to-end pipeline (hardcoded IP, no discovery/pairing)

- [x] Windows: capture → raw PCM → UDP to a configured IP:port.
- [x] Android: UDP listen → jitter buffer → AudioTrack.
- **Goal:** hear laptop audio through the earbuds at all. This was treated
  as the riskiest technical step per the original design — implemented
  first, before investing in UX.
- **Implemented in:** `windows-app/src/capture/`, `windows-app/src/network/audio_sender.rs`,
  `android-app/.../network/AudioReceiver.kt`, `android-app/.../audio/JitterBuffer.kt`,
  `android-app/.../audio/PlaybackTrack.kt`.

## Phase 2 — Discovery

- [x] mDNS advertise (Windows, `mdns-sd` crate) / NSD browse (Android),
      replacing a hardcoded IP with device list + selection.
- **Implemented in:** `windows-app/src/network/discovery.rs`,
  `android-app/.../discovery/NsdDiscovery.kt`.

## Phase 3 — Pairing & security

- [x] Pairing-code handshake over the TCP control channel, session-key
      derivation (HKDF), ChaCha20-Poly1305 encryption of the UDP payload —
      per `protocol-spec.md` §5.
- **Implemented in:** `windows-app/src/protocol/crypto.rs`,
  `windows-app/src/network/control_channel.rs`,
  `android-app/.../network/ControlChannel.kt`,
  `android-app/.../network/Crypto.kt`.

## Phase 4 — Reliability

- [x] Heartbeat, reconnect-with-backoff, persisted last-paired device.
- [x] Foreground service + wake lock + multicast lock on Android.
- [x] Network-change handling — a `ConnectivityManager` default-network
      callback tears down the session and restarts NSD discovery when the
      phone moves between networks (Wi-Fi to hotspot, SSID switch, DHCP
      renewal onto a new subnet), debounced so one transition causes one
      restart rather than several. Surfaced to the UI as a distinct
      `NETWORK_CHANGED` status.
- [x] Reconnect backoff supervision — a dropped session now schedules its
      own retry (1s doubling to a 30s ceiling, reset on a successful stream
      or a network change). Previously reconnection depended on NSD
      happening to re-announce the service, which it has no obligation to
      do.
- **Implemented in:** `windows-app/src/config.rs`,
  `windows-app/src/network/control_channel.rs` (heartbeat),
  `android-app/.../service/RelayService.kt`,
  `android-app/.../service/ReconnectBackoff.kt`.

## Phase 5 — Jitter buffer & latency tuning

- [x] Basic fixed-depth jitter buffer with sequence-gap fade-to-silence.
- [x] User-configurable jitter-buffer depth (Android Settings screen —
      `state/SettingsStore.kt`, `ui/SettingsScreen.kt`). Applies on the next
      reconnect, not to an already-running buffer.
- [x] Timestamp-based clock-drift correction over long sessions. The
      receiver now regulates smoothed buffer depth back to the target by
      dropping or duplicating a single PCM frame at a time (~21µs, versus
      the ~10ms click a whole-chunk correction would cause), gated on
      observed session time from each packet's `timestamp_ms`
      (`protocol-spec.md` §3), with a deadband and rate limit so ordinary
      network jitter provokes no correction. Covered by a simulation test
      suite in `android-app/.../audio/ClockDriftTest.kt`.
- [x] Low/Balanced latency-mode toggle in the Windows UI (`ui/settings.rs`)
      — changes the capture chunk size (~5ms vs ~10ms) live, no restart.

## Phase 6 — UI polish

- [x] Configurable `egui` UI (Windows) — three tabs: Home (status, pairing
      code, streaming on/off), Settings (capture-device picker, latency
      mode, paired-device management), About (version, build commit/date,
      GitHub link, license/third-party info). See `windows-app/src/ui/`.
- [x] Configurable Compose UI (Android) — matching three-screen shell:
      Home, Settings (output-device picker, jitter depth, paired-laptop
      management), About (version, build commit/date, GitHub link, license
      info). See `android-app/.../ui/`.
- [x] Output/capture device selection on both sides — the laptop picks
      which output device's audio to relay; the phone picks which output
      device (Bluetooth/wired/USB/speaker) to route to, or leaves it on
      Android's automatic routing.
- [ ] Further visual polish (this is a functional, minimalist pass — not a
      full design system) is open for follow-up.

## Phase 7 — Optional / future (not built)

Tracked as ideas, not committed work — open an issue if you want to pick one
up:

- Opus codec fallback for weak/congested networks.
- Process-specific loopback capture ("capture just this app").
- Browser-based receiver as a zero-install alternative.
- Packaging/release pipeline: signed portable `.exe`, signed APK, GitHub
  Releases automation.

## How to contribute against this roadmap

- Unchecked items above are the best source of well-scoped issues. Comment
  on or open an issue referencing the phase before starting significant
  work, so effort isn't duplicated.
- When you finish an item, check it off in the same PR and add a note to
  `CHANGELOG.md`'s `[Unreleased]` section.
- Phase 0 items can only be checked off with a real on-device test — see
  `CONTRIBUTING.md` → "Hardware verification".
