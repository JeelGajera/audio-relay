# android-app

Kotlin/Gradle app: NSD (mDNS) discovery, TCP control-channel client,
sequence-aware jitter buffer, low-latency `AudioTrack` playback, and the
foreground service that holds it all together with the screen off. See
`docs/architecture.md` (repo root) for the full design rationale and
`protocol-spec.md` for the wire format.

## Building

Requires Android Studio (or the command-line SDK) with `compileSdk 34`.

```sh
./gradlew assembleDebug
```

The committed `gradle-wrapper.jar` was generated with `gradle wrapper
--gradle-version 8.7` from an official system Gradle install — not
hand-written — pinning the project to Gradle 8.7 the normal way.

## Running

Install the debug APK on a device with an already-paired Bluetooth
speaker/earbuds, launch it, and it starts the foreground service
immediately — no Start button needed, matching `windows-app`'s "just an
exe" philosophy. It'll show discovered laptops as they appear on mDNS; pick
one, enter the pairing code shown on the laptop, and audio should start
routing to whatever Bluetooth device is already connected.

## Module map

| Package | Responsibility |
|---|---|
| `network/AudioPacket.kt` | UDP audio packet header decode (pure Kotlin) |
| `network/ControlMessage.kt` | TCP control-channel message types (`kotlinx.serialization`) |
| `network/Crypto.kt` | HKDF session-key derivation, repair proof, ChaCha20-Poly1305 payload decryption |
| `network/ControlChannel.kt` | Pairing handshake + heartbeat client |
| `network/AudioReceiver.kt` | UDP receive loop → decrypt → jitter buffer → playback loop |
| `audio/JitterBuffer.kt` | Sequence-aware jitter buffer with silence concealment (pure Kotlin) |
| `audio/PlaybackTrack.kt` | Low-latency `AudioTrack` wrapper (`USAGE_MEDIA`) |
| `discovery/NsdDiscovery.kt` | mDNS browse for `_audiorelay._udp` |
| `state/PairedDeviceStore.kt` | Persisted device ID + paired laptops (`SharedPreferences`) |
| `state/RelayState.kt` | Process-wide observable state shared between the service and the UI |
| `service/RelayService.kt` | Foreground service wiring everything together |
| `ui/` | Minimal Compose UI |

## Testing

```sh
./gradlew testDebugUnitTest
./gradlew lint
```

Local unit tests (`src/test/`) cover `AudioPacket`, `ControlMessage`,
`Crypto`, and `JitterBuffer` — all pure Kotlin/JDK code with no Android
framework dependency, so they run on the plain JVM without Robolectric or a
device/emulator.

**These are the only parts of this app verified in this repository's
history.** They were compiled and run with the *exact* Kotlin 1.9.24
compiler and the exact `kotlinx-serialization`/`kotlinx-coroutines`
versions this project declares (not just reasoned about), including a
**cross-implementation known-answer test**
(`CryptoTest.decryptPayload matches the windows-app reference vector`) that
decrypts a ChaCha20-Poly1305 ciphertext generated by
`windows-app/src/protocol/crypto.rs`'s Rust implementation and confirms
Android's `Cipher.getInstance("ChaCha20-Poly1305")` recovers the exact same
plaintext — real evidence the two independent implementations agree on the
wire format, not just each internally consistent.

Everything that touches the Android framework (`AudioReceiver`,
`PlaybackTrack`, `NsdDiscovery`, `RelayService`, `MainActivity`,
`StatusScreen`) has **not** been compiled or run against the real Android
Gradle Plugin/SDK in this repository's history — the sandbox this was
originally written in has outbound network access for most Maven
repositories (Maven Central, the Gradle Plugin Portal) but not
`dl.google.com`, which is where the Android Gradle Plugin and the Android
SDK components themselves are published, so `./gradlew` cannot get past
plugin resolution there. It's been written carefully against the
documented APIs and manually reviewed, but treat it as unverified until
someone with normal internet access (or Android Studio) builds and runs
it — see `docs/roadmap.md` Phase 0 and `CONTRIBUTING.md` → "Hardware
verification".

## Known limitations (tracked in `docs/roadmap.md`)

- No adaptive jitter-buffer depth or clock-drift correction yet — see
  `JitterBuffer.kt`'s class doc.
- No `ConnectivityManager` network-change listening yet (relies on the
  heartbeat timeout to notice a dead connection and retry via mDNS).
- Pairing-code UI is a bare dialog, not polished.
